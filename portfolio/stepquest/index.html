The short version

01

StepQuest turns everyday walking into a fortress. Your phone's step count becomes coins, and the coins buy and upgrade towers that defend a castle against waves of enemies. Each month is a new season, with one battlefield and 20 levels. Your defence carries over from level to level, so a month of walking builds one fortress.

The players are children and younger teenagers, and the game reads their health data. That shaped everything. Steps are converted to coins on the phone and never leave it. The whole game works offline without an account. There are no ads, purchases, streaks or reminder notifications, and an under-13 can't go online until a parent agrees.

The project started from a written specification approved on 24 October 2026, with an eight-milestone roadmap that tackled the riskiest technical question first. Five milestones are complete: the game is in the hands of TestFlight testers with real steps from Apple Health and a shared leaderboard.

How the game works

02

  1. Walk

    Steps are read from Apple Health, iPhone and Apple Watch combined without double-counting. Steps typed in by hand don't count.

  2. Earn

    Every 100 steps is a coin, plus a small bonus for opening the game on any 3 days of a week. Nothing else pays coins.

  3. Build

    Buy, upgrade, move and sell towers on the season's build pads, and buy charges for signature abilities.

  4. Defend

    A 3–5 minute battle of 5–8 waves. Towers fire on their own; you time the abilities. Lose, adjust and retry at once.

Designing the economy

03

Paced for a real child's week

The design reference player has a phone only and records about 4,000 steps on a school day and 7,000 at weekends. English schools are phone-free by default, so school-day walking mostly goes unrecorded, and the game never encourages carrying a phone in school.

  • Very active, or Apple Watch730 coins a week · 11 days
  • Reference player370 a week · 21 days
  • Light walker235 a week · 33 days

Days to afford a defence that beats Level 20. The gold mark is the target: week 3. Light walkers should still reach the Level 10 boss.

Hard to outspend

Build space is fixed for each season and sized so that a fully upgraded defence costs about 1.5 times what the reference player needs. Very active walkers reach that ceiling early, and later levels then need good placement and well-timed abilities rather than more coins. The ceiling is never shown: there's no "maxed out" message.

Tuned as data, never mid-season

Every price, rate and threshold is one setting in a data file. Settings are versioned by season month, so a change made in November waits until 1 December and never changes the rules partway through a season. An audit traced each economy value in the spec to the file that holds it.

Key decisions, and why

05

  1. A battle that always plays out the same way

    The battle runs as a plain simulation, separate from what's on screen, at 20 ticks a second. It uses whole numbers only (positions in thousandths of a tile) and no randomness, so the same level with the same taps always ends identically, on any device.

    Why: one choice made four features simple. A save stores just the starting setup and a log of the player's taps, so closing the app mid-battle and reopening it replays to the exact same moment. Pause and 2× speed only change how fast ticks are fed in. Tests can check that an enemy dies on a particular tick. And a scripted stand-in player plays every level at different budgets to check the balance.

  2. A step ledger that can't pay twice

    For each day, the game records how many steps it has already paid for. Each time it opens, it re-reads the last 7 days and pays only the difference. A day's paid total never goes down.

    Why: late Apple Watch syncs, re-reads, clock changes and time-zone changes can't pay the same steps twice or take coins away. The ledger is written before the save, so a crash between the two can only underpay, never double-pay.

  3. Our own HealthKit plugin

    No maintained Godot 4 HealthKit plugin existed, so we wrote one: a small C++ extension with Swift that reads daily step totals, skips hand-typed entries, and also handles Sign in with Apple.

    Why: the game needs only daily totals, and a few hundred lines of our own are far easier to audit for privacy than a large third-party plugin. It was milestone 1, so if it had failed the project would have stopped before anything else was built.

  4. The server does the scoring

    Players can't write to the leaderboard. The game sends a season, a level and the castle health left; a database function checks it, works out the points and writes the row. Wins out of order, from another season or with impossible health are refused.

    Why: one round trip, protected by the database's own row-level security rules. A test checks that the server's points tables still match the game's.

  5. Everything is data

    Towers, enemies, abilities, levels, waves, routes, badges, usernames and every economy value live in JSON files, checked when the game starts. A mistake becomes a readable error naming the file and field, not a crash mid-battle.

    Why: next month's season is mostly new data and art, not new code, and JSON is easy to review and ready to move into remote configuration.

  6. Stopping one phone's wins being handed around

    Testing showed a loophole: sign friends in one after another on the same phone, and each new account would inherit its wins. The fix: each account has its own game on the phone. The first account to sign up takes the phone's game, once only. Later accounts start fresh, and the game played while signed out is never given to anyone.

    Why: it keeps Sign out (which the first TestFlight build had to leave out) without reopening the loophole. The step ledger stays one file per phone, so steps are never paid twice whichever game is in use.

How it's built

06

One codebase in Godot 4, a thin native plugin per platform, and Supabase for the optional online features. Four layers, each depending only on those below it.

  • Economy and savessrc/economyCoins, the shop, the step ledger, monthly seasons, badges, saving and resuming.draws anything
  • Rulessrc/simRuns battles, works out stars and points, loads and checks content.touches the screen, reads the clock or uses randomness

How the project is run

07

Eight milestones, each ending in something that can be run and checked on a real iPhone before the next begins. Three release stages each answer one question before the next adds cost: is it fun, does the economy work with real steps, and is it ready for the public?

  1. 1 Done

    Feasibility test

    Today's steps from Apple Health, shown in a bare Godot app on a real iPhone.

  2. 2 Done

    Battle core

    Data-driven, deterministic simulation; one tower, one enemy, win and defeat.

  3. 3 Done

    Full battle rules

    All towers, enemies and the boss; upgrades, abilities, waves, 2× speed, stars and points.

  4. 4 Done

    Season prototype

    20 levels, unlocks, the shop, save and resume. Playtested to answer "is it fun?"

  5. 5 Done

    Real steps and a leaderboard

    HealthKit, the step ledger, tutorial, badges, season reset, accounts and server scoring. A week on TestFlight.

  6. 6 In progress

    Online features

    Sign out and progress sync are in; weekly boards, profiles and remote configuration next.

  7. 7 Next

    Test season

    A full month with testers to tune pacing to land near week 3.

  8. 8 Later

    Version 1

    Data-protection adviser review, accessibility pass, commissioned art, App Store.
